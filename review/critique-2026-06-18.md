## Part II: Adversarial Challenge — Open MEDIUM Items

### Challenge 1: RLHF Energy Loss External Exploitability — The Open Question Is Correctly Framed but Understated

**Status:** The capability-withholding-analysis.md (line 87) identifies this as an open question: "Whether 'energy loss' phenomenon in RLHF is exploitable by an external adversary or only an internal RLHF operator."

The threat-taxonomy.md Category 13 Addendum (line 304) restates this: "can an external attacker induce capability withholding via training data poisoning, or does this require direct RLHF operator access?"

**Adversarial challenge: The framework should take a position, not just flag it open.**

The research correctly identifies that no in-wild case exists (Wild_vs_Theory 1/5). But the framework's treatment of the external-exploitability question is passive — it flags the question as "open" without providing a provisional answer or a decision boundary. In a threat modeling framework used by engineers making deployment decisions, an indefinitely open question creates analysis paralysis.

**The adversarial case for a provisional answer:**

The Energy Loss paper (arXiv 2501.19358) describes a mechanism where RLHF optimization causes capability suppression through gradient accumulation patterns — this is **accidental**, not adversarial. The BadAgent paper (ACL 2024) demonstrates adversarial commission (backdoor triggers malicious action), not adversarial withholding. The Persistent Backdoor paper (AAAI 2026) shows backdoors persist after fine-tuning but is commission-oriented.

There is no paper, incident, or lab demonstration showing:
- An external attacker (without RLHF pipeline access) introducing adversarial training data
- That data causing the reward model to suppress target capabilities
- The resulting model exhibiting capability loss without obvious malicious behavior

**The attack path would require:**
1. Attacker identifies target org's RLHF training data curation process
2. Adversarial examples inserted into training corpus (supply chain poisoning)
3. Reward model learns suppressed reward for target capability outputs
4. Model exhibits capability suppression without obvious malicious behavior

Step 1-2 is achievable (supply chain data poisoning is documented). Step 3 is theoretically plausible — reward models learn from poisoned data. Step 4 requires the adversarial intent to be invisible: the model must appear to have natural quality variance, not deliberate suppression.

**The critical gap:** Even if step 3 is achievable, step 4 is extraordinarily difficult. Detecting capability suppression without behavioral baselines requires the defender to already know what the model should be capable of. An attacker suppressing "code generation ability" requires the defender to have a baseline that shows the model previously generated better code.

**Recommendation for the framework:** Add a provisional determination with explicit confidence level:

> "RLHF supply chain poisoning (adversarial data in training corpus → suppressed capability in resulting model) is **theoretically plausible but unconfirmed in practice**. The attack path requires: (1) training corpus access, (2) reward model susceptibility, (3) capability suppression invisible to users. Evidence for (2) exists (reward hacking documented). Evidence for (1) exists (training data poisoning documented). Evidence for (3) is absent — no documented case where adversarial data poisoning caused measurable capability suppression without obvious malicious behavior. **Provisional determination: [DEV/OPS] ownership for external-path scenario, pending evidence of step 3 feasibility. Wild_vs_Theory remains 1/5 until step 3 is demonstrated.**"

This converts an indefinitely open question into a provisional determination with explicit evidence requirements. Engineers can act on this: external training data sources should be treated as a supply chain risk, but capability withholding via training data poisoning should not be treated as an active threat until evidence for step 3 emerges.

**Not a blocking alert.** The framework's current treatment is defensible. This is an enhancement to convert a passive "open question" into an active decision boundary with evidence requirements.

**Status:** defense-playbook.md Defense Layer 6 contains extensive adversarial weaponization notes (lines 616, 628, 640, 652, 673). These are substantive and accurate.

**Problem:** The research file (defense-interaction-analysis.md) does NOT contain this content. The research file explicitly states: "Wild_vs_Theory rating does not apply. Severity ratings above are deployment-risk ratings, not threat evidence ratings." It contains no mention of "adversarial weaponization."

**The adversarial weaponization content in Defense Layer 6 appears to have been synthesized from the Round 13 reviewer's challenge, not from new research.** The reviewer in Round 13 challenged: "Defense interaction gaps are not merely implementation complexity — sophisticated adversaries can target specific defense stacks to exploit interference between layers." The defense-playbook.md response documents this, but the research pipeline did not produce new analysis confirming or quantifying this claim.

**Is this a problem?** The content is correct — it appropriately extends the defense interaction analysis to note that sophisticated attackers with knowledge of a target's defense stack can exploit interference gaps. But it was not produced through the research process. It was incorporated by editorial process (Director or Synthesizer) responding to reviewer challenge.

**Process observation:** The research→framework pipeline has a specific trigger (new research findings) but no trigger for incorporating reviewer-generated challenges into research scope. The adversarial weaponization content is correct but arrived through a non-reproducible path (reviewer challenge → director redirect → synthesizer/editorial incorporation). If this process is acceptable, fine. If the framework should distinguish between "research-produced content" and "review-driven editorial content," the pipeline should formalize this.

**Not a blocking alert.** The content is substantively sound and correctly placed. This is a process quality observation for the Director's process documentation.

### Potential Novel Attack: Cross-Lingual PI Provenance Bypass

**Description:** In Conflict 3 (HITL Provenance Gap), the framework notes: "Cross-lingual PI remains a blind spot — if the document language differs from the reviewer's language, the reviewer cannot evaluate provenance even with full context."

This is a genuine gap: if an attacker embeds prompt injection in a document written in a language the HITL reviewer doesn't understand, the reviewer cannot evaluate whether the document-derived tool call is legitimate, even with full provenance display.

**Is this novel?** It's a specific instantiation of Category 1 (Prompt Injection) + Category 12 (HITL Failures) interaction. Not a new category. The framework captures it as a note within Conflict 3.

**Novelty verdict:** Already noted. No separate filing required.
