# Reviewer Critique: LLM Threat Modeling — Round 3 (Pilot Readiness Audit)

**Review Date:** 2026-06-17
**Reviewer Role:** Red-Team Adversarial Review
**Synthesis Reviewed:** research/synthesis.md (Round 4), full framework v1.1 (framework.md, threat-taxonomy.md, attack-trees.md, risk-matrix.md, defense-playbook.md, assessment-template.md)
**Critique Focus:** Pilot readiness validation — AIBOM operationalization, assessment template completeness, Chain C plausibility, small-team readiness estimate

---

## Executive Summary

The framework v1.1 is substantially more mature than v1.0. All 9 Round 2 adversarial findings have been addressed: invented probability estimates removed, AIBOM trust anchor field added, RAG sanitization corrected to load-time, Chain C extended, HITL UX revised, underground PI market added, defense control types distinguished, AIBOM freshness triggers added. The threat taxonomy is saturated — no new categories should be opened.

However, the framework now faces a **new class of failure: the assessment template cannot be reliably completed by a 3-person engineering team with no ML security expertise.** The v1.1 revisions introduced specific fields and checks that are operationally underspecified — operators know what to fill in but not how to fill it in. The AIBOM `key_verified_via` field is the clearest example: the schema requires it, the assessment checks for it, but no external attestation service actually provides a verifiable path.

**Three critical operational gaps prevent pilot use:**
1. AIBOM `key_verified_via` field is required but not serviced — no HuggingFace model today can satisfy this field with a working verification path
2. The assessment template asks teams to score risks (1–5) and rate controls (infrastructure vs. alignment) without providing scoring rubrics or worked examples
3. The framework spans 5 documents with no internal cross-reference anchors — a non-expert completing the assessment template cannot locate the threat definitions they need to respond accurately

## Adversarial Findings

### Finding 1: AIBOM `key_verified_via` Field Is Required But Not Serviced — CRITICAL / BLOCKING

**Severity:** CRITICAL — blocks pilot use
**Framework documents:** defense-playbook.md (SC-DEF-1), assessment-template.md (§1.5)
**Finding type:** Operational specification absent — the field is defined but the verification path it requires does not exist

**The contradiction:**

The assessment template §1.5 requires operators to verify `key_verified_via` and specifies valid values: `huggingface_verified_publisher / sigstore / pgp / none`. The AIBOM schema in defense-playbook.md requires the `key_verified_via` field. The v1.1 revision note explicitly calls this out as the fix for the Round 2 CRITICAL finding.

**The problem:** None of these verification paths actually work today for a typical HuggingFace deployment:

**A. HuggingFace Verified Publisher Badge:**
- Requires the publisher to have verified their domain ownership with HuggingFace
- As of June 2026, verified publisher status on HuggingFace only confirms the publisher controls a domain — it does NOT verify the model weights themselves are untampered
- A typosquatted model (e.g., `MistralAI/Mistral-7B-v0.3` vs `MistralAI/Mistral-7B-Instruct`) can have a verified publisher badge if the attacker sets up domain verification for `mistralai-attacker.com`
- The verified publisher badge is an identity anchor, not a provenance anchor — it tells you who uploaded the model, not whether the model is the intended artifact
- **The synthesis (correctly) does not claim otherwise, but the assessment template does not warn about this limitation**

**B. Sigstore Attestations:**
- Sigstore's `cosign` tool can produce model attestations, but HuggingFace does not natively integrate Sigstore attestations into its model hosting
- As of June 2026: no documented workflow exists for a HuggingFace model publisher to publish a Sigstore attestation that an operator can verify via the standard Sigstore infrastructure (`rekor.sigstore.dev`)
- The Sigstore + HuggingFace integration is a research/publishing gap, not an operational capability
- **Attempting this verification path today would require the operator to contact the model publisher directly for attestation artifacts that may not exist**

**C. PGP Key Fingerprint:**
- The AIBOM schema includes `publisher.pgp_key_fingerprint` but provides no keyserver lookup path
- No documented workflow exists for an operator to verify a HuggingFace model's PGP fingerprint against a keyserver
- Most HuggingFace model publishers do not publish PGP keys tied to their model artifacts
- **This verification path is theoretical, not operational**

**Walkthrough with Mistral-7B-v0.3:**

> Operator deploys `mistralai/Mistral-7B-Instruct-v0.3` from HuggingFace:
> 1. Operator checks for "verified publisher" badge — Mistral AI has one ✓
> 2. Operator sets `key_verified_via: "huggingface_verified_publisher"` in AIBOM ✓
> 3. **Problem:** The verified badge confirms `mistralai/Mistral-7B-Instruct-v0.3` was uploaded by Mistral AI. It does NOT confirm the weights are the official release. A typosquatted `MistralAI/Mistral-7B-Instruct-v0.3` (impersonating capital 'AI') with a verified publisher badge set up by the attacker would ALSO satisfy this check.
> 4. **Problem:** No Sigstore attestation exists on the model repository. The `key_verified_via` field cannot be populated with `sigstore` because the attestation doesn't exist.
> 5. **Problem:** No PGP key is published on the model page. The `pgp_key_fingerprint` field cannot be populated.

The assessment template §1.5 would have the operator mark:
- `key_verified_via`: YES (populated — but with a verification path that doesn't actually verify provenance)
- `typosquatting check performed`: PARTIAL (only checked for verified badge, which can be impersonated)

**Challenge to Researcher (Round 4 follow-on):** Audit the four `key_verified_via` options. For each, produce a worked example showing: (1) the exact steps an operator takes, (2) the actual output of those steps, (3) what that output confirms and what it does NOT confirm. If any option cannot produce a working example in under 10 minutes of investigation, state explicitly that it is "not currently operational" and remove it as a valid `key_verified_via` value.

**Fix required:** The `key_verified_via` field must be revised to reflect what actually exists operationally. If Sigstore + HuggingFace integration is not operational, `sigstore` cannot be a valid value. The assessment template must distinguish between "verification path exists but requires manual effort" (sigstore, pgp) and "verification path is identity-only, not provenance" (huggingface_verified_publisher). The only honest valid value for most HuggingFace deployments today is `none` — with explicit guidance that this means the model must be treated as unverified and requires manual security review before deployment.

### Finding 2: Assessment Template Scoring Rubric Absent — HIGH / BLOCKING

**Severity:** HIGH — blocks pilot use
**Framework document:** assessment-template.md
**Finding type:** Operational specification absent — the template asks for ratings without defining what the ratings mean

**The problem:**

The assessment template asks operators to make four types of qualitative judgments without providing a scoring rubric:

1. **Risk ratings (1–5)** in Sections 1.1, 1.2, 1.4, 1.5:
   > *"Indirect PI risk rating (1–5): 1=none, 5=critical"*
   > *"Agency risk rating (1–5): 1=no agency, 5=full system access"*

2. **Control type classification** in Section 3:
   > *"Control Type: Technical (infrastructure) or Alignment"*

3. **Threat status** in Section 2:
   > *"MITIGATED / PARTIAL / UNMITIGATED"*

4. **Defense implementation verification** in Section 3:
   > *"Method: How is this control implemented?"*

**Why this blocks a non-expert pilot:**

A 3-person engineering team with no ML security expertise has no internal calibration for these ratings. Without a rubric:

- An operator will score the same deployment differently on different days ("is this a 3 or a 4?")
- Two operators on the same team will produce inconsistent assessments
- The output risk matrix (Section 5) will be arbitrary, not comparable across teams
- Risk acceptance decisions (Section 5.2) made from uncalibrated ratings have no defensible basis

**What a scoring rubric must contain:**

For risk ratings, the template needs explicit decision criteria. Example:

> **Indirect PI Risk Rating (Section 1.1):**
> - **1:** System does not retrieve external content (no RAG, no search, no document ingestion)
> - **2:** System retrieves external content but has explicit privilege separation (retrieved content cannot invoke tools by infrastructure design)
> - **3:** System retrieves external content; privilege separation enforced via prompt instruction only (not infrastructure)
> - **4:** System retrieves external content; retrieved content can invoke tools; no HITL required
> - **5:** System retrieves external content; retrieved content can invoke tools with elevated permissions; no HITL

**Specific ambiguous fields requiring rubric definitions:**

1. **"instruction density" scoring** — The defense playbook and assessment template reference scoring documents for "instruction density" (PI-DEF-2, assessment template §3.1), but no definition exists. A non-expert cannot score what they cannot define.

2. **"PARTIAL" control implementation** — Section 3 asks teams to mark controls as YES / PARTIAL / NO. For a non-expert, "PARTIAL" is the path of least resistance — they will mark everything PARTIAL because they don't know what full implementation looks like. The template must define what "PARTIAL" means for each control.

3. **"Control Type: Alignment vs. Technical (infrastructure)"** — This distinction is the most important new concept introduced in v1.1, and the template provides only a one-line definition. A non-expert cannot reliably classify their controls without a worked example showing the same defense implemented both ways.

**Fix required:** Add a scoring rubric appendix to the assessment template with:
- Decision trees for each risk rating (1.1, 1.2, 1.4, 1.5)
- A worked example: "Here is the same RAG privilege separation implemented as alignment control vs. infrastructure control — which does your deployment use?"
- A "PARTIAL implementation" definition for each primary defense (what minimum criteria must be met before PARTIAL becomes YES)
- The instruction density scoring method (even a simple heuristic: count of instruction-resembling phrases per 1000 tokens)

### Finding 3: Framework Document Cross-References Are Non-Functional — MEDIUM / PILOT OBSTACLE

**Severity:** MEDIUM — creates friction but does not block
**Framework document:** assessment-template.md
**Finding type:** Navigation failure — cross-references point to documents without section anchors

**The problem:**

The assessment template references other framework documents throughout:
- Section 1.1: *"See threat-taxonomy.md §Category 1 (Prompt Injection) for threat definitions"*
- Section 2: *"Chain A — see attack-trees.md for full kill chain"*
- Section 3.1: *"PI-DEF-2 privilege separation — see defense-playbook.md §PI-DEF-2"*

These cross-references are correct in principle but fail in practice because:

1. **No section anchors exist** — the reference "threat-taxonomy.md §Category 1" requires the operator to open the file, scroll or search for "Category 1", read it, and return. For a non-expert using the assessment for the first time, this navigation burden means they will skip the references and answer from their own understanding — which may not match the framework's definitions.

2. **The 5-document framework requires constant context-switching** — completing the assessment template correctly requires simultaneously consulting 5 documents. This is reasonable for a security expert; it is overwhelming for a 3-person engineering team doing a one-time threat model exercise.

3. **No "quick reference" artifact exists** — the framework notes "reading order recommendation" in framework.md, but no single-page quick reference summarizes: the 12 threat categories with one-line definitions, the 3 attack chains with their primary nodes, and the primary defenses with their control types.

**Specific navigation failures that will cause non-expert errors:**

- Section 2 asks operators to mark threat status for "Chain A", "Chain B", "Chain C" — but the assessment template does not define what "Chain A" means. An operator who hasn't read attack-trees.md (which they won't — it's not in the reading order for a first pass) will answer based on their own mental model.

- Section 3.1 asks about PI-DEF-2 sanitization: *"Verify sanitization occurs at LOAD TIME (before chunking), not index time."* An operator who only has the assessment template (the document the team is supposed to use directly) won't know why this distinction matters unless they cross-reference defense-playbook.md, where the explanation exists.

- Section 1.5 asks about AIBOM `key_verified_via` but the valid values (huggingface_verified_publisher / sigstore / pgp / none) are defined in defense-playbook.md, not in the assessment template itself.

**Fix required:** The assessment template must be a **standalone working document**, not a cross-reference aggregator. For each question that requires external context, either:
- Include the minimal definition inline (what is Chain A? one line), OR
- Produce a single-page "threat model quick reference" that operators can keep alongside the assessment template

The scoring rubric (Finding 2) should live in the assessment template itself, not require cross-referencing to other documents.

### Finding 4: Chain C Extension — Theoretically Sound but Not Validated Against Real Multi-Agent Frameworks — MEDIUM

**Severity:** MEDIUM
**Framework document:** attack-trees.md (Chain C extension)
**Finding type:** Theoretical plausibility without empirical grounding

**What the extension adds (v1.1):**
- Tool return value injection: agent calls a tool that returns attacker-controlled content, which poisons the calling agent
- N-agent propagation: compounding compromise probability as agents chain
- System prompt contamination: shared infrastructure contaminates all agents
- Privilege escalation via context manipulation: agent exploits context to elevate visible permissions

**Why this is plausible:**

The Chain C extension is consistent with the Christian Schneider (Jan 2026) agentic attack chain model and OWASP Top 10 for Agentic Applications 2026. Tool return value injection is a documented attack surface in LangGraph and AutoGen — when a tool returns unstructured content that becomes context for a subsequent LLM call, that content is processed without instruction hierarchy protection in many implementations.

**Why validation is missing:**

The extension was synthesized from threat modeling first principles, not reverse-engineered from documented multi-agent framework behavior. The following questions cannot be answered from the current research:

1. **LangGraph specifically:** LangGraph's `ToolNode` and `FunctionNode` patterns — does the tool return value enter the agent's context without provenance metadata? If so, an attacker who compromises one tool's output can poison subsequent agent calls. The framework asserts this is true but does not cite LangGraph-specific validation.

2. **AutoGen specifically:** AutoGen's `AssistantAgent` and `UserProxyAgent` communicate via a shared messaging layer. Does the framework's "N-agent propagation" match AutoGen's actual context window sharing model? The framework assumes yes but does not cite AutoGen's architecture documentation.

3. **CrewAI specifically:** CrewAI uses role-based agents with explicit task delegation. Does the "privilege escalation via context manipulation" path match CrewAI's permission model? A CrewAI agent that is told it is a "code reviewer" might have elevated permissions — can context manipulation cause the agent to re-interpret its own role?

4. **The N>2 propagation claim:** The compound probability formula (P_compromised = 1 - ∏(1-P_agent_n)) is theoretically correct but has no empirical basis. What is the actual P_agent for real multi-agent frameworks? The 2025 study on automated red-teaming (69.5% success rate) covered prompt injection broadly but did not isolate multi-agent context propagation as a separate threat category.

**Why this matters for the pilot:**

Engineering teams building multi-agent systems (LangGraph, AutoGen, CrewAI) will read the Chain C extension and apply it to their specific framework. If the extension's attack paths don't accurately map to the framework they're using, they will either:
- Over-apply defenses that aren't relevant to their architecture, OR
- Under-apply defenses that the extension correctly identifies but their framework mitigates differently

**Challenge to Researcher (Round 4 follow-on):** Walk through Chain C against ONE specific multi-agent framework (recommend LangGraph as the most widely used). Show the actual attack path: which component receives the injection, how it propagates to the next agent, what the final impact is. If the attack path works as modeled, document the specific LangGraph API calls that would be exploited. If the attack path doesn't work as modeled, revise the extension to match the actual architecture.

### Finding 5: Pilot Team Will Get Stuck at Three Specific Points — PILOT OBSTACLE

**Severity:** MEDIUM — predictable failure mode
**Framework document:** overall framework usability
**Finding type:** Non-expert comprehension failure — predictable points where teams will fail or produce incorrect output

Based on a mental walkthrough of the assessment template with a hypothetical 3-person engineering team (1 backend engineer, 1 ML engineer, 1 product manager/security-minded):

**Where they will get stuck:**

**Stuck Point 1: Section 1.1 — Trust Level Labels**

> *"Are different content sources labeled with different trust levels? YES / PARTIAL / NO"*

The ML engineer knows their RAG pipeline returns documents from a vector database. The backend engineer doesn't know if those documents are labeled. The product manager doesn't know what "trust levels" means in this context. The team debates for 20 minutes, marks PARTIAL (the path of least resistance), and moves on. Their answer doesn't reflect whether their pipeline actually has provenance metadata — they just couldn't agree on what the question meant.

**Stuck Point 2: Section 3.1 — PI-DEF-2 Control Type Classification**

> *"PI-DEF-2: RAG context labeling — Control Type: Technical (infrastructure) or Alignment"*

The defense playbook explains this distinction clearly (lines 88-98 in defense-playbook.md). But the team is using the assessment template, which provides a one-line definition. The backend engineer says "we implemented it in code so it's technical." The ML engineer says "it's a prompt instruction so it's alignment." The product manager has no basis to arbitrate. They mark PARTIAL and move on.

The actual answer matters: if it's alignment-only, the control is dependent on model robustness and should not be counted as an independent layer. But the team has no way to determine this without reading defense-playbook.md carefully AND understanding what "infrastructure enforcement" means in their specific pipeline.

**Stuck Point 3: Section 5 — Residual Risk Summary**

> *"Rank | Threat | Residual Risk Level | Reason | Recommended Action"*

The team has completed 4 sections of binary/ternary responses. Now they're asked to synthesize this into a ranked list of the top 3 residual risks with explanations. A 3-person team with no threat modeling experience will produce:
- Generic risks ("prompt injection is our biggest concern") that don't reflect their specific architecture
- Recommendations that are vague ("implement more controls") without specificity
- Inconsistent severity reasoning between items

This section requires threat modeling judgment that the framework has not provided a template for. A non-expert cannot synthesize 4 sections of checkbox answers into a defensible risk prioritization without guidance.

**What would help:**

For Stuck Point 1 and 2, the inline scoring rubrics (Finding 2) address the problem directly.

For Stuck Point 3, Section 5 needs a decision framework:
> *"Start with your YES responses in Section 2 (UNMITIGATED threats). For each, review the corresponding risk rating from Section 1. Threats with rating ≥ 4 AND UNMITIGATED status are your top priorities. For each, the Recommended Action is the Primary Defense from the defense-playbook.md for that threat category."*

Without this guidance, Section 5 will be skipped, completed incorrectly, or used to justify decisions that aren't grounded in the framework's own analysis.

### Finding 6: "Wild vs. Theory" Metric Applied Inconsistently — MEDIUM

**Severity:** MEDIUM
**Framework document:** .control.json (director metric definition), risk-matrix.md
**Finding type:** Metric definition exists but is not applied in the framework itself

**The problem:**

The director's `.control.json` defines a "Wild vs. Theory" metric:
> *"Rate each finding on 1-5 scale for deployment reality. Apply to: attack techniques, defense effectiveness claims, threat agent capabilities. Minimum filing threshold for HIGH or CRITICAL rating: Wild_vs_Theory >= 3."*

This is a strong methodology guard. It forces the framework to distinguish between theoretical attacks (academic, no documented in-wild cases) and confirmed production threats. However:

1. **The metric is not visible in any framework document** — the assessment template, risk matrix, and threat taxonomy do not include a "Wild vs. Theory" rating field. The director's metric lives in the project's control file, not in the framework that operators will use.

2. **The metric is not applied to the attack tree findings** — the synthesis (Round 4) catalogs real-world incidents and assigns confidence levels, but does not apply the 1-5 Wild_vs_Theory scale to the attack techniques in the threat taxonomy. For example:
   - "Zero-click email prompt injection (EchoLeak)" would score 4-5 on the scale (confirmed in-wild, CVSS 9.3)
   - "N-agent propagation via tool return injection" would score 2 on the scale (theoretically described, plausible in production, not confirmed in wild)
   - The framework treats both as HIGH/CRITICAL without distinguishing their empirical grounding

3. **Defense effectiveness claims don't carry Wild_vs_Theory ratings** — the v1.1 revision correctly removed the ">90% reduction" claim, but the remaining defense effectiveness descriptions (e.g., "HIGH (reduces but does not eliminate PI exploitability)") don't carry explicit empirical grounding. An operator reading "PI-DEF-1: HIGH effectiveness" might interpret this as a different confidence level than intended.

**Why this matters for pilot credibility:**

A 3-person team completing the assessment will produce risk decisions. If those decisions are based on threat ratings that conflate theoretical and confirmed attacks, the resulting threat model will be miscalibrated. Engineering leadership reviewing the threat model will not know which HIGH ratings are based on documented incidents versus theoretical worst-cases.

**Fix required:** Apply the Wild_vs_Theory metric to the threat taxonomy explicitly. For each threat category in threat-taxonomy.md and each defense effectiveness claim in defense-playbook.md, add a field:
> `Wild_vs_Theory: <1-5> — <one-line rationale>`

This makes the empirical grounding visible in the framework documents themselves, not just the director's control file.

## DIRECTOR ALERT

**ALERT (BLOCKING):** The AIBOM `key_verified_via` field is currently a compliance theater trap. The assessment template requires it, the AIBOM schema defines it, and the director's `.control.json` flags it as a critical validation gap — but none of the four defined verification paths (huggingface_verified_publisher / sigstore / pgp / none) provide a working provenance verification for a typical HuggingFace deployment today. An engineering team that completes the assessment template and populates `key_verified_via: "huggingface_verified_publisher"` for a HuggingFace model will believe they have verified their supply chain when they have only verified the publisher's domain ownership. This is not a research gap — it is an operational specification failure that the next researcher+synthesizer iteration must resolve by either (a) documenting the exact verification workflow that works today, or (b) honestly labeling the field as non-operational for HuggingFace deployments until Sigstore integration is productized.
