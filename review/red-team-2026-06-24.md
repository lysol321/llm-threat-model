# Red Team Review — LLM Threat Model

**Date:** 2026-06-24
**Scope reviewed:** `synthesis/framework.md`, `assumptions.md`, `asset-inventory.md`, `attack-surface-catalog.md`, `threat-taxonomy.md`, `attack-trees.md`, `risk-matrix.md`, `defense-playbook.md`, `assessment-template.md`, `quick-reference.md`.

## Verdict

**REQUEST CHANGES before calling this pilot-ready.**

The framework is strong on structure: explicit assumptions, assets, attack surfaces, kill chains, defense ownership, and production constraints. The core security model is directionally right: prompt injection + excessive agency, supply-chain compromise, and multi-agent context propagation are the correct high-leverage concerns.

But the current corpus has several contract-level inconsistencies that would mislead a 3-person engineering team during a real assessment. The biggest issue: the new ISC / validator-harness threat was added to the taxonomy and defense playbook, but not fully propagated into the risk matrix, quick reference, framework priority summary, or worksheet. The second issue: OWASP 2025 IDs are stale/misassigned in multiple places.

## Findings

### Critical — Taxonomy numbering is broken after adding ISC

**Evidence:** `synthesis/threat-taxonomy.md` has:
- Category 3 = Internal Safety Collapse (`threat-taxonomy.md:86`)
- Category 4 = Supply Chain (`threat-taxonomy.md:125`)
- Category 4 = Data and Model Poisoning (`threat-taxonomy.md:155`)
- Category 13 = Defense Control Type Confusion (`threat-taxonomy.md:321`)
- Category 13 Addendum = Capability Withholding (`threat-taxonomy.md:338`)

This breaks every `Cat N` reference across the corpus. Example: `assumptions.md:86-88` still says supply-chain threats are Category 3, but taxonomy now uses Category 3 for ISC. `quick-reference.md:16-17` also still presents Supply Chain as #3 and Data/Model Poisoning as #4.

**Why it matters:** An engineering team using the worksheet will map assets/surfaces to the wrong threats. This is not cosmetic; it corrupts traceability.

**Required fix:** Decide canonical numbering. Recommended: preserve OWASP-aligned numbering and make ISC either `Category 14` or an addendum under Output/Agency rather than inserting it at #3. Then update every `Cat N` reference programmatically.

### Critical — ISC is missing from the operational assessment path

**Evidence:**
- ISC is marked **CRITICAL** with Wild_vs_Theory 5/5 in `threat-taxonomy.md:86-121`.
- ISC surfaces are marked CRITICAL in `attack-surface-catalog.md:69-88`.
- ISC defenses exist in `defense-playbook.md:243-320`.
- But `risk-matrix.md` has no ISC row in Critical/High/Medium/Low tiers.
- `framework.md:184-217` priority summary has no ISC row.
- `assessment-template.md:51-107` threat surface checklist has no ISC / TVD / validator-harness section.
- `quick-reference.md:10-26` still says “12 Threat Categories” and omits ISC entirely.

**Why it matters:** The docs say ISC is critical, but the thing the pilot team actually uses (`assessment-template.md`) cannot surface or score it. That means the most recently added critical threat is invisible in the workflow.

**Required fix:** Add ISC to:
1. risk matrix with likelihood, impact, owner, regulatory note,
2. framework critical/high priority summary,
3. quick reference category list and decision tree,
4. assessment template Section 2 + Section 3 control evaluation + Section 4 scoring rubric.

### Critical — Risk tiers contain entries whose scores contradict their tier

**Evidence:** `risk-matrix.md:100-109` places these under “Tier 4: Lower Risks (Risk Score 1–6)”:
- Purchased PI Template Attack: score **15**
- Defense Control Type Confusion: score **12**

**Why it matters:** This directly defeats prioritization. A score-15 threat belongs in High, not Lower. A score-12 threat is Medium, not Lower.

**Required fix:** Move score-15 Purchased PI Template Attack to High, merge it into Direct PI, or explicitly mark it as a sub-factor rather than standalone. Move Defense Control Type Confusion to Medium or High depending on final score.

### High — OWASP 2025 mappings are stale / wrong

**Evidence:** Official OWASP 2025 list maps:
- LLM05 = Improper Output Handling
- LLM07 = System Prompt Leakage
- LLM08 = Vector and Embedding Weaknesses
- LLM09 = Misinformation
- LLM10 = Unbounded Consumption

Current docs use older/mixed IDs:
- `threat-taxonomy.md:221` labels DoS as `LLM09`; in OWASP 2025 this should be `LLM10: Unbounded Consumption`.
- `framework.md:79-81` says OWASP LLM09 is “Misuse of LLM for malicious content generation” and LLM10 is “Dependency on LLM-generated output for critical decisions.” This does not match official OWASP 2025 naming.
- `threat-taxonomy.md:173`, `205`, and `286` omit / misalign LLM07, LLM08, and LLM05 labels.

**Why it matters:** Regulatory/security teams will cross-check these. Wrong external taxonomy IDs undermine credibility.

**Required fix:** Add an explicit “OWASP 2025 mapping” table and update all inline labels. If the framework intentionally diverges from OWASP, say so and keep OWASP IDs separate from internal category IDs.

### High — Quick reference is stale and dangerous as the first-read artifact

**Evidence:** `framework.md:124` tells teams to start with `quick-reference.md`, but `quick-reference.md`:
- says “12 Threat Categories” (`quick-reference.md:10`), while framework says 13 + addendum (`framework.md:97`);
- omits ISC, Defense Control Type Confusion, Capability Withholding, and newer surfaces;
- ends with “Quick Reference v1.2” despite header version 1.3 (`quick-reference.md:126`).

**Why it matters:** The quick reference is the document most likely to be read. If it is stale, the whole model is stale in practice.

**Required fix:** Treat quick reference as generated from canonical taxonomy/risk matrix, or remove it from the recommended reading order until it is synced.

### Medium — Markdown table corruption reduces usability

A script found 8 malformed table groups. Examples:
- `threat-taxonomy.md:125` includes stray `</parameter>` in a heading.
- `threat-taxonomy.md:217` has a 4-column row in a 3-column table.
- `threat-taxonomy.md:247-254` mixes `||` and `|` table row starts.

- `risk-matrix.md:135` has `ifAPI` typo.
- `risk-matrix.md:177-178` visual says “Quorum Exhaus” instead of “Quota Exhaustion”.

**Why it matters:** Broken tables are not just presentation errors. They make the document harder to review, export, and ingest into tooling.

**Required fix:** Run a markdown table normalization pass and add a simple CI/script check for inconsistent pipe counts outside code blocks.

---

### Medium — Chain C evidence language overstates “confirmed” status

**Evidence:** `threat-taxonomy.md:241` says LangGraph source “confirms” ToolNode returns unsanitized tool output to shared messages state. `quick-reference.md:65` says the pattern is structurally confirmed. The docs also acknowledge no published CVE addresses Chain C specifically (`threat-taxonomy.md:243`).

**Why it matters:** The structural risk is real, but the wording can read like a product vulnerability claim rather than a default architecture risk. That invites pushback.

**Required fix:** Use sharper wording: “architecturally plausible and source-confirmed data-flow risk; exploitation depends on deployment-specific tool/output trust and agent permissions.” Keep high priority for multi-agent systems, but avoid implying a CVE-grade vulnerability in LangGraph defaults unless one exists.

---

### Medium — “System prompt is the security boundary” assumption conflicts with the framework’s own security principle

**Evidence:** `assumptions.md:169-171` says system prompt can be the security boundary. But `assumptions.md:45-48`, `defense-playbook.md:95-99`, and the broader framework correctly state alignment-based controls are weaker than infrastructure controls.

**Why it matters:** A non-expert reader may infer that system prompts are acceptable security boundaries if engineered for non-extractability. They are not. They are policy hints unless backed by infrastructure enforcement.

**Required fix:** Rewrite D7: “Some deployments incorrectly treat system prompt as a security boundary; the framework treats prompt secrecy as IP/information-disclosure control, not an authorization boundary.”

---

### Medium — Attack-tree likelihood uses pseudo-probability math after rejecting probabilities

**Evidence:** `attack-trees.md:426-429` introduces `P(Agent N+1 compromised | Agent N compromised)` and `P(any in chain)` after saying no synthetic probability figures are presented (`attack-trees.md:9-12`).

**Why it matters:** It reintroduces mathematical framing without data. A reviewer will call this out as exactly the problem earlier rounds fixed.

**Required fix:** Replace with qualitative text: “risk increases with each unsanitized handoff; chain length creates more opportunities for missed detection and privilege escalation.”

## Positive notes

- The trust-boundary model is much stronger than most LLM threat models: user input, retrieved context, tool outputs, inter-agent messages, MCP, A2A, and logs are all called out explicitly.
- Defense control type distinction is excellent. The alignment-vs-infrastructure split is the right lens.
- HITL provenance requirement is strong and practical.
- Asset inventory and attack surface catalog are the right shape for a pilot worksheet.
- Supply-chain section correctly calls out the AIBOM/Sigstore gap: provenance is not behavior verification.

## Recommended correction order

1. Freeze canonical taxonomy IDs and update all `Cat N` references.
2. Thread ISC through risk matrix, framework summary, quick reference, and assessment worksheet.
3. Fix risk tier contradictions in `risk-matrix.md`.
4. Align OWASP 2025 IDs/names.
5. Sync document versions and downgrade pilot status until synced.
6. Normalize markdown tables and add a table-integrity check.

## Bottom line

The model is conceptually strong, but the corpus is currently internally inconsistent. I would not hand this to a pilot team yet. Fix the taxonomy/risk/worksheet synchronization first; then it becomes a credible pilot artifact.
