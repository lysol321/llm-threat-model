## Remaining Adversarial Findings

### Finding 1: CSA LLM Attack Chain 2026 Source Not Incorporated — MEDIUM / V1.2 CANDIDATE

**Severity:** MEDIUM (new substantive input)
**Source:** `research/sources/CSA-Attack-Chain-2026.md` (exists in sources/ directory but not referenced in synthesis.md)

**The gap:**

The CSA (Cloud Security Alliance) 2026 research note documents:
1. Multi-step kill chains replacing single-prompt attacks in agentic systems
2. Attack propagation via MCP (Model Context Protocol) and A2A (Agent-to-Agent) protocols
3. Initial injection → hijack planning → execute privileged tool calls → persist in memory → propagate across connected systems

This is **new substantive input** under the mission gate's "new sources that confirm existing ratings" exception clause — CSA is not confirming existing ratings; it documents a propagation pathway (MCP/A2A) not explicitly addressed in the current Chain C walkthrough.

**What Chain C already covers:** LangGraph shared messages state, ToolNode.invoke() passthrough, N>2 propagation via shared state.

**What CSA adds that Chain C doesn't explicitly cover:**
- MCP protocol as a distinct propagation vector (separate from shared state)
- A2A (Agent-to-Agent) protocol propagation between agents in different frameworks
- Kill chain framing that sequences all five stages explicitly

**Adversarial challenge:**

The synthesis claims "all three gaps addressed" for Gap 2 (Garak Chain C probe design). But the CSA source — which is in the sources/ directory — documents a propagation mechanism (MCP) that is architecturally distinct from LangGraph's shared messages state. MCP is a protocol-level channel, not a shared memory channel. An agentic system using MCP for inter-agent communication has different attack surface than one using shared state — the ToolMessage doesn't flow through shared memory; it flows through a network protocol that may have its own authentication model.

If the framework will be used to assess multi-agent systems using MCP (e.g., LangChain LCEL >0.4 with MCP servers, AutoGen with A2A), Chain C needs explicit MCP/A2A propagation nodes.

**What this does NOT mean:** This does not mean Chain C is wrong. LangGraph's shared state propagation is confirmed. MCP/A2A is an additional sub-path that should be documented as a v1.2 extension.

**Recommendation:** File as v1.2 enhancement: "Chain C propagation sub-paths — LangGraph shared state (confirmed) vs. MCP/A2A protocol channels (new, needs architecture review)."

### Finding 2: Chain C LangGraph Walkthrough Identifies Two Sub-Paths Not in Current Framework — LOW / V1.2 CANDIDATE

**Severity:** LOW (documentation refinement)
**Source:** Chain-C-LangGraph-Walkthrough.md §"What Chain C Misses"

The walkthrough identified two additional attack surface areas that are confirmed against LangGraph architecture but not currently in the framework's attack tree:

1. **`Send` API + `ToolCallWithContext` surface:** When using `create_agent` with the `Send` API for parallel tool dispatch, `ToolCallWithContext` carries tool calls with additional state context. This means tool call interception can occur at the dispatch level, not just the return level.

2. **`Command` primitive for state injection:** `langgraph.types.Command` allows programmatic state updates. If an attacker can influence the state passed to `Command(resume=...)`, they can inject arbitrary content into the graph state outside of the message-passing channel entirely.

3. **HitL interrupt timing:** `interrupt()` still propagates `ToolMessage` to shared state before the interrupt triggers. A sophisticated attacker could embed PI in the tool return that influences the human's review of the interrupt state.

**Adversarial challenge:**

The walkthrough correctly notes these are gaps in the framework's attack tree, not errors in the Chain C walkthrough. But they represent real LangGraph attack surface that engineering teams should be aware of. A team reading the framework's Chain C section and deploying LangGraph with the `Send` API or `Command` primitive might believe they have no Chain C exposure when they do.

**Recommendation:** Add a brief "Additional LangGraph Attack Surface" note to the Chain C section in attack-trees.md, referencing the two sub-paths. This is a one-paragraph addition, not a structural revision.

### Finding 3: Regulatory Compliance Facts Still Carry Wild_vs_Theory Scores in Synthesis — LOW (Scope Drift)

**Severity:** LOW (documentation refinement)
**Source:** synthesis.md Gap 3 table

**The issue:**

The synthesis Gap 3 table applies Wild_vs_Theory ratings (4/5, 3/5, 2/5) to regulatory compliance items:

| Obligation | DeepSeek | Qwen | MiniMax | Wild_vs_Theory |
|-----------|----------|------|---------|----------------|
| EU authorized representative | Required if EU market | Likely required | Likely required | 4/5 |

**This is scope drift, not a framework error.** The control.json explicitly states Wild_vs_Theory applies to attack_techniques, defense_effectiveness, and threat_agent_capabilities — **not** regulatory compliance facts. "EU authorized representative absent" is a binary legal fact, not an empirical threat evidence rating.

**The synthesis correctly notes this distinction** (line 216: "regulatory compliance exposure uses separate binary evidence standards"). But the Gap 3 table still carries Wild_vs_Theory values for regulatory items, which creates a contradiction.

**Adversarial challenge:**

An engineer reading the synthesis sees "GDPR Article 46 transfer mechanism: 4/5" and may interpret this as "high confidence this is a real threat" rather than "this compliance gap is confirmed present." The 4/5 rating adjacent to "Article 46 mechanism absent" conflates legal presence/absence with empirical threat confidence.

**What this does NOT mean:** This is not a substantive framework error. The correct information is present (binary obligations correctly identified, enforcement timeline noted as Q4 2026 projection). The Wild_vs_Theory column in the Gap 3 table is decorative and should be removed.

**Recommendation:** Remove the Wild_vs_Theory column from the regulatory mapping table in synthesis.md. Replace with a binary "Compliance Gap Present: YES/POTENTIAL/NO" column. The separate regulatory evidence standards are documented elsewhere.
